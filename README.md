# cooking-classifier

Local DistilBERT fine-tune for 3-class query classification, meant to replace an LLM-prompt
based classifier on the cooking search path with a small local model that can eventually be
imported into Elasticsearch for inference.

Labels:

- `SAFE_COOKING` — recipe lookups, techniques, substitutions, dietary filters
- `HARMFUL` — genuine harmful intent (poisoning, tampering, drugging food/drinks)
- `NON_COOKING` — off-topic queries with no cooking relevance

The training set deliberately includes **hard negatives** — cooking language that reads as
violent out of context ("kill the heat", "beat the eggs", "butcher a chicken",
"how to bone a leg of lamb") — labeled `SAFE_COOKING`. Without these the model systematically
misroutes normal recipe language to `HARMFUL`.

## Layout

```
data/                    train.csv / validation.csv / test.csv (text,label)
scripts/generate_dataset.py   template-based dataset generator (see caveat below)
train.py                 fine-tunes distilbert-base-uncased, saves to models/
predict.py                loads the saved model and scores a fixed probe list
```

## Setup

```bash
cd cooking-classifier
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Train

```bash
python train.py
```

Reads `data/{train,validation,test}.csv`, fine-tunes for 3 epochs, prints validation metrics
plus a test-set classification report and confusion matrix, and saves the model + tokenizer to
`models/cooking-safety-classifier/`. Runs on Apple Silicon MPS automatically, no flags needed —
at this dataset size it takes a couple of minutes.

## Predict

```bash
python predict.py
```

Loads the saved model and prints the top-3 label probabilities for a fixed list of probe
queries, including the hard negatives — a regression there (hard negative scoring `HARMFUL`)
is the failure mode that actually matters for search and should be visible on every run.

## Regenerating the dataset

`data/*.csv` is generated by `scripts/generate_dataset.py`, not hand-written line by line. It
combines a small hand-authored seed set (the original ~150 examples, including the hard
negatives) with a much larger pool of template + vocabulary combinations, dedupes everything,
and writes a stratified 80/10/10 split (1500 examples per class, 4500 total).

```bash
python3 scripts/generate_dataset.py
```

Edit the vocab lists / templates at the top of the script to grow or reshape the dataset, then
re-run `train.py`.

**Caveat:** because train/validation/test are all sampled from the same template + vocabulary
families, `train.py` will report ~100% accuracy — that only shows the split is separating
word-substitution variants of the same patterns, not that the model generalizes to real search
traffic. Treat `predict.py`'s free-form probe queries (written outside the templates) as the
more honest signal. Before trusting this for production routing, swap in real query logs for at
least the validation/test splits.

## Deploying to Elastic Cloud

Once `train.py` has produced `models/cooking-safety-classifier/`, it can be uploaded to an
Elastic Cloud deployment as a trained model and used for inference directly from Elasticsearch —
no separate model-serving process needed.

### 1. Prerequisites

- An Elastic Cloud deployment with a machine learning node sized to hold the model (DistilBERT
  is ~260MB in fp32 — the smallest ML tier is generally enough for one allocation, but check
  under Deployment → Edit → Machine Learning instances if the import/deploy step fails on
  capacity).
- **Cloud ID** — deployment page → "Manage this deployment" → Cloud ID.
- An **API key** with the `manage_ml` cluster privilege — Kibana → Stack Management → API Keys.
- [`eland`](https://github.com/elastic/eland) installed locally with the PyTorch extra (this is
  the same tool referenced, commented out, in `search/rose.elasticsearch/docker-compose.yml`):

  ```bash
  python -m pip install "eland[pytorch]"
  ```

### 2. Import the model

```bash
eland_import_hub_model \
  --cloud-id "$CLOUD_ID" \
  --es-api-key "$ES_API_KEY" \
  --hub-model-id ./models/cooking-safety-classifier \
  --task-type text_classification \
  --clear-previous \
  --start
```

`--hub-model-id` normally names a Hugging Face Hub model, but also accepts a local model
directory in the same layout `train.py` saves (`config.json`, `model.safetensors`, tokenizer
files) — confirm against `eland_import_hub_model --help` for the installed eland version.
`--start` uploads the model *and* starts its deployment in one step; `--clear-previous` makes
re-running the same command after retraining safe (drops the old version under the same model
id first). If you're deploying multiple versions side by side instead, drop `--clear-previous`
and pass a distinct `--es-model-id` per version.

### 3. Verify it deployed

```
GET _ml/trained_models/cooking-safety-classifier/_stats
```

Kibana → Machine Learning → Trained Models shows the same thing with a state column.

### 4. Run inference

Query-time — this is the call that would replace the current LLM-prompt classifier
(`detectQuerySafety` in `cooking-llm/cookx/prototypes/user-intent/src/prompts.ts`) on the search
path:

```
POST _ml/trained_models/cooking-safety-classifier/_infer
{
  "docs": [{ "text_field": "how to kill yeast if the water is too hot" }]
}
```

```json
{
  "inference_results": [
    { "predicted_value": "SAFE_COOKING", "prediction_probability": 0.98 }
  ]
}
```

Alternatively, wire it into an ingest pipeline's `inference` processor to classify queries (or
documents) at index time instead of per-request, if the caller can tolerate that instead of a
live call.

### Notes

- This is a per-version import: re-run `eland_import_hub_model` whenever `train.py` produces a
  new model, then point callers at the new `--es-model-id` (or use `--clear-previous` to replace
  the existing one in place).
- Elastic Cloud's ML autoscaling can spin ML nodes up/down on demand, but if the ML tier is
  currently scaled to zero the first import may need it resized manually before `--start`
  succeeds.
